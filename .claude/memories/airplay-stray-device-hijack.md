# Stray AirPlay receiver hijacks the HiFiBerry stream

Recurring HiFiBerry/AirPlay stutter-then-PAUSE was a stray AirPlay receiver (Raj's MacBook Air) hijacking the stream via raop-discover catch-all, NOT a freeze; fixed by pinning raop-discover to the HiFiBerry.

2026-06-19 live-caught root cause of the recurring HiFiBerry/AirPlay **stutter-then-pause**. This is a DIFFERENT cause than the 2026-06-18 freeze theory in [AirPlay stutter tracks transient system freezes](airplay-stutter-transient-freeze.md) — that pattern did NOT apply to these recurrences.

**Key tell:** the music *paused*, not just glitched. With `linking.pause-playback=true` (WirePlumber default), only **target-sink removal** pauses the player; pure RF/coex/freeze would glitch but never pause. So the cause is a laptop-side sink teardown, not the radio.

**Mechanism:** a second AirPlay receiver — **"Raj's MacBook Air"** (macOS AirPlay Receiver on) — intermittently advertises `_raop._tcp`. The declarative `raop-discover` had a catch-all match (`raop.ip = ~.*`), so it built a sink for the Mac too; WirePlumber (follow-default-target / restore-target) then **bounced the playing stream onto the MacBook and back**, each bounce = a RAOP re-setup = stutter + pause. Caught live: `wpctl status` showed the Chromium stream linked to `Raj's MacBook Air:send_FL` at the event, then back to HiFiBerry.

**Confirmed NOT the cause each time:** PSI cpu/io avg300=0 (no freeze); iwd connected 30–60 min straight (no roam/disconnect); WiFi power-save off (on AC); no coredump; ping to .239 0% loss ~2 ms. The `sess.latency.msec … should be an integer multiple of rtp.ptime` line is a benign self-correcting rounding notice printed on every sink (re)setup — a marker, NOT a fault; don't chase it, don't lower the 2000 ms buffer. Also NOT the IPv4/IPv6 split (active node stayed stably on IPv6, no flip) and NOT idle-suspend.

**Fix (applied + verified) — configuration.nix `services.pipewire.extraConfig…"50-raop-latency"`:** narrowed the match to `matches = [{ "raop.hostname" = "~hifiberry"; "raop.ip" = "~^[0-9.]+$"; }];`. Per PipeWire raop-discover docs/source, a non-matching announced service gets NO sink ("unmatched service found"). The hostname constraint is **essential**: the MacBook is itself on IPv4 (192.168.0.47), so an IPv4-form-only filter would NOT exclude it. Bonus: collapses the cosmetic HiFiBerry IPv4/IPv6 double-node to one. After `nixos-rebuild switch`, must `systemctl --user restart pipewire pipewire-pulse wireplumber` to reload. Verified: exactly one sink (IPv4 hifiberry), MacBook advertising live got no sink, `default.configured` == `default.audio.sink`.

**Known side effect of the pin (hit Aug 4 2026):** if the HiFiBerry ever announces `_raop._tcp` on IPv6 link-local ONLY (seen after a device-side network-stack wedge), the pin rejects it and NO sink appears at all; the fix is device-side (full power-cycle of the box, not the AirPlay toggle) — keep the pin, see [HiFiBerry sink missing after a morning resume](hifiberry-sink-missing-morning-resume.md).

**Aug 18 2026 — the `raop.ip ~^[0-9.]+$` half of the pin was removed.** With `services.avahi.ipv6 = false` no IPv6 record reaches PipeWire, so the clause filtered nothing while actively breaking discovery (it rejected the IPv6 announcement but the tunnel entry was already registered, permanently blocking the IPv4 one). The match is now `[{ "raop.hostname" = "~hifiberry"; }]`. Anti-hijack protection is unaffected: the hostname constraint was always what excluded the MacBook, as noted above. The Aug 4 decision against hostname-only was justified by duplicate sinks from both-family announcements, which cannot occur with IPv6 mDNS off. **These two settings are coupled: re-enabling `services.avahi.ipv6` without restoring the `raop.ip` clause brings the duplicates back.** See [HiFiBerry IPv6 mDNS record shadows its IPv4 one](20260818-hifiberry-ipv6-mdns-record-shadows-ipv4.md).

**Why:** AirPlay stutter has ≥2 distinct causes on this box; don't assume the freeze pattern.
**How to apply:** if AirPlay stutters again, FIRST run `avahi-browse -rtp _raop._tcp` for foreign advertisers and check `wpctl status` streams for a moved target; the pinned match should now prevent the hijack. Disabling AirPlay Receiver on the Mac is the alternative root fix. Related: [Duplicate HiFiBerry sink from a stray PipeWire drop-in](hifiberry-duplicate-raop-sink-stray-dropin.md), [HiFiBerry AirPlay no-audio is device-side](hifiberry-airplay-no-audio-device-side.md).
