# HiFiBerry sink missing after a morning resume

HiFiBerry sink absent after a morning resume/reconnect — raop-discover is mDNS-announcement-driven; fixed with a resume hook that restarts pipewire.

Jul 13 2026: The recurring "HiFiBerry not in audio outputs when I get to work" (the ritual of opening hifiberry.local and toggling AirPlay to make it appear) is **not** a device problem — the device is online and advertising fine.

**Root cause:** `libpipewire-module-raop-discover` (loaded in the *pipewire* daemon via `services.pipewire.extraConfig`) is **event-driven on fresh mDNS announcements**. It only creates the sink when the device (re)announces. A morning resume / network reconnect produces no announcement, so no sink appears. Toggling AirPlay on the device forces a re-announce → sink appears — that's why the ritual works. Proven from logs: pipewire ran all night but created the raop-sink only at the instant of the toggle.

**Verified kick:** `systemctl --user restart pipewire` forces an *active* mDNS browse → sink returns in **~1 s** (avahi already has the device cached). A full pipewire restart is the reliable hammer; wireplumber stays up and reconnects.

**Fix (in `configuration.nix`):** `systemd.services.airplay-rescan` — `After`+`WantedBy = suspend.target` (systemd has no `wakeup.target`; this is the "run on the way back up" idiom), `ExecStart = systemctl --user restart pipewire.service`. Chose this (Option 2) over a static `module-raop-sink` (Option 1) because a static sink stays visible at home where the device is absent and can silently swallow audio (WirePlumber's disappear→fallback rescue never fires on an always-present sink).

**BUG found in review (Jul 13, same day):** the first version used `User = username` + `Environment=XDG_RUNTIME_DIR=/run/user/%U` — but in a **system** unit `%U` expands to the *service manager's* UID (0), explicitly NOT influenced by `User=` (systemd.unit(5) specifiers). Live unit showed `XDG_RUNTIME_DIR=/run/user/0`; `systemctl --user` then fails with "Failed to connect to user scope bus". The unit had never actually fired through a resume — the "verified kick" above was the *manual* restart only. The documented way to reach another user's manager from a root unit is `systemctl --user --machine=<user>@.host …` (systemctl(1) `-M`, since v248; needs systemd-run/systemd-stdio-bridge on unit PATH — NixOS default unit PATH already includes systemd). **Fixed same day with that form** (root unit, no `User=`/`Environment=`; also trimmed unreachable hibernate/hybrid-sleep targets — zram-only machine). Expected journal cosmetic: one transient `run-uNNNN.service` + PAM login entry per resume. First real-world confirmation still pending: check `systemctl status airplay-rescan` after the next morning resume.

**Bonus finding:** discovery auto-negotiates `raop.encryption.type = auth_setup` (NOT `none`, despite mDNS `et=0,4`), `raop.transport = udp`, port `7000`. So a static sink would have needed `auth_setup` — the discover auto-negotiation is worth keeping.

**Caveat:** resume-only. If the laptop is *powered off* overnight instead of suspended, the hook won't fire and would need a boot-time rescan ordered after the network is up. Watch whether the morning ritual actually disappears after a real resume.

**Jul 21 2026 — third trigger found: `nixos-rebuild switch`.** Minutes after a switch (which reloaded dbus-broker + restarted systemd-udevd), the raop sink silently vanished while the device was still announcing fine on both IPv4+IPv6 (avahi-browse confirmed) — so removal events / broken browse sessions can kill the sink too, not just missing announcements. Streams quietly failed over to the next sink (now unpinned, they follow default). Same kick works: `systemctl --user restart pipewire` → sink back in ~3 s, then `pactl set-default-sink raop_sink.hifiberry.local.192.168.0.239.7000` to restore. If this recurs after ordinary rebuilds, consider extending airplay-rescan or just re-kick manually.

**Aug 4 2026 — fourth variant: device announces IPv6-only, the anti-hijack pin filters it → NO amount of pipewire restarts helps.** After the morning WiFi flap the HiFiBerry's Shairport re-registered `_raop._tcp` **only on IPv6 link-local** (hostname A record still resolved on IPv4, so the box looked "online"; `avahi-browse -rpt _raop._tcp` showed no `;IPv4;` row over 15 s). The stray-device fix ([Stray AirPlay receiver hijacks the HiFiBerry stream](airplay-stray-device-hijack.md)) requires `raop.ip ~^[0-9.]+$`, so the IPv6-only announcement is discovered and correctly-per-config rejected: airplay-rescan fired on all three resumes, pipewire restarted cleanly, still no sink. **Raj's AirPlay-toggle ritual did NOT fix it** (toggle restarts Shairport inside the device's wedged network stack → re-registers IPv6-only again). **Fix: full power-cycle of the HiFiBerry box** → IPv4 announcement returned. Diagnosis discriminator: `avahi-browse -rpt _raop._tcp | grep ';IPv4;'` — if absent it's device-side, don't touch our config. Second wrinkle: after IPv4 came back, the running raop-discover did NOT create the sink on its own (stale browse session, same class as the Jul 21 finding) — one `systemctl --user restart pipewire` finished the job. Decision: do NOT relax the pin to hostname-only to tolerate IPv6-only announcements; both-family announcements would then create duplicate hifiberry sinks (see [Duplicate HiFiBerry sink from a stray PipeWire drop-in](hifiberry-duplicate-raop-sink-stray-dropin.md) for why duplicates hurt).

**Aug 10 2026 — IPv6-only wedge recurred** (second occurrence, 6 days after the first). Same diagnosis path and same fix worked: no `;IPv4;` row in avahi-browse → power-cycle the box → one pipewire restart → sink back. This is now an established recurring mode, not a one-off; check the IPv4 discriminator FIRST whenever the sink is missing.

**Aug 18 2026 — fifth variant, and it supersedes the Jul 13 root cause above.** Sink absent after the morning resume with the device announcing fine on BOTH families (IPv4 discriminator present, so not the Aug 4/Aug 10 wedge). Cause is host-side: `module-raop-discover` keys its tunnel list by mDNS service name alone, so whichever family announces first claims the name and the pin's IPv6 rejection left a registered tunnel that blocked the IPv4 record forever. IPv6 link-local rejoins ~5 s before DHCP-gated IPv4 on every resume, so it lost deterministically. Fixed with `services.avahi.ipv6 = false` plus dropping the `raop.ip` clause. The Jul 13 "resume produces no announcement" reading was almost certainly this same shadowing seen from outside, and the Jul 21 / Aug 4 "stale browse session" behaviour is the same bug on the avahi-client-reconnect path. Full mechanism and source references: [HiFiBerry IPv6 mDNS record shadows its IPv4 one](20260818-hifiberry-ipv6-mdns-record-shadows-ipv4.md).
